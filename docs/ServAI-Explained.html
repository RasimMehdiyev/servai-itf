1. The Big Picture

ServAI is a monitoring dashboard for a grocery-picking robot called ROBI. Think of it like a security camera control room, but instead of watching cameras, a supermarket employee watches what the robot is doing in real time and reviews how it performed over the past days.

The system has two main screens:

  • Live Screen — Watch ROBI work right now. See what it's picking up, where it's going, and step in if something goes wrong.
  • History Screen — Look back at past orders. See charts, statistics, and ask an AI assistant questions like "Why did order #42 take so long?"
Key concept: In a real deployment, ROBI would be a physical FANUC robot arm in a supermarket, sending live data to this dashboard. During development, we don't have a real robot, so we replay a recording of a real robot session. The dashboard can't tell the difference — it behaves exactly as it would with a real robot.

2. The Three Servers

To run ServAI, three separate programs need to be running at the same time. Think of them like three employees with different jobs:

Server Analogy What it does Port
Vite Dev Server The shop window Serves the website you see in your browser 5173
WebSocket Server The security camera feed Replays robot activity in real time (dev only — replaced by the real robot in production) 8765
RAG/AI Server The smart analyst Generates AI summaries and answers questions using a local AI model 5175

A "port" is like an apartment number in a building. Your computer is the building (at address "localhost"), and each server lives in a different apartment. The browser knows which server to talk to by using the right port number.

Independence rule: The charts, numbers, and order data work even if the AI server is completely off. The AI is a bonus layer — it adds captions and chat, but nothing breaks without it.

3. The Fake Robot (WebSocket Replay Server)

ws-test-server.js

Since we don't have a real robot plugged in during development, we have a clever workaround: a replay server.

What is a WebSocket?

A normal website works like sending letters — you ask for a page, the server sends it back, done. A WebSocket is more like a phone call — once connected, both sides can talk to each other at any time without hanging up. This is essential for live updates because the robot needs to continuously tell the dashboard what it's doing.

How the replay works

We have a file called grocery_logs.txt that contains a recording of a real robot session — every message the robot sent, with timestamps. The replay server reads this file and plays it back like a movie:

grocery_logs.txt (recording) ws-test-server.js (replay) Your browser | | | | "Stage 1: going to shelf" | | | timestamp: 10:03:01.234 -------> | Wait the right amount | | | of time, then send -----> | Shows "Going | "Stage 3: 4 detections" | to all browsers | to the shelf" | timestamp: 10:03:05.891 -------> | -----> | | | | Shows "Finding | "Stage 11: gripper SUCCESS" | -----> | the item" | timestamp: 10:03:12.445 -------> | | | | | Shows "Picking | | | it up"

What the replay server also does

  • Appends orders to a shared file: Every time the robot completes a "cycle" (picks up one item), the server appends a record to data/orders.json with timing, status, and step details. This file is the shared data store — see the box below.
  • Classifies outcomes: It decides if an order was successful (green), had warnings (amber — like 0 detections on first try but recovered), or failed (red — gripper dropped the item).
  • Simulates failures: After every 2nd cycle, it intentionally injects a fake gripper failure to make the data more realistic.
  • Handles intervention: Sometimes the robot can't find an item and needs a human to help. The server pauses and waits for the employee to click a button in the app.
  • Serves data via HTTP: The History screen fetches order data and daily statistics through regular web requests (not WebSocket) from this server.
Orders are independent from the robot connection. The file data/orders.json is a persistent data store on disk. Once an order is written there, it stays forever — regardless of whether the WebSocket server, the replay, or any robot is running. Both the WebSocket server and the RAG/AI server can read this file and serve its contents via their own HTTP endpoints. In production, order records would be written by whatever system processes real robot events (a backend service, a database, or the robot controller itself). The dashboard only reads from the data store — it never depends on a live robot connection to show historical orders.
In production: This replay server would be replaced by a real connection to the FANUC robot controller. The frontend code wouldn't change at all — it just receives messages in the same format. The order data store would likely be a database instead of a JSON file, but the API shape would remain the same.

4. The Frontend (What You See on Screen)

The frontend is built with React, a popular library for building interactive websites. Instead of writing one giant HTML file, React lets you build small, reusable pieces called components.

Think of components like LEGO bricks. A "Card" component is a rounded white box. A "StatusChip" is a small colored label. You snap them together to build screens.

How the files are organized

Starts the whole app. App.jsx ← Sets up the page structure and navigation routes. index.css ← Global styles and color variables. components/ ui/ ← Reusable building blocks Card.jsx ← White rounded box used everywhere SmartCaption.jsx ← Renders AI text with tooltips and citations StatusChip.jsx ← Small colored badge ("Delivered", "Failed") ... layout/ ← Page structure TopBar.jsx ← The bar at the top with "ROBI" and status BottomTabBar.jsx ← The Live / History / Settings tabs at the bottom ScreenContainer ← Wrapper that centers content and adds padding features/ live/ ← Everything for the Live screen history/ ← Everything for the History screen day-details/ ← Everything for the Day Details screen hooks/ ← Reusable logic for fetching data useRobotSocket.js ← Connects to the WebSocket server useRagCaption.js ← Fetches an AI caption from the RAG server useRagChat.js ← Streams a chat conversation with the AI services/ ← Business logic messageMapper.js ← Translates raw robot messages into screen state orderStore.js ← Manages the orders data context/ DataSourceContext ← Shares the WebSocket connection across all components lib/ terms.js ← Dictionary of technical terms (for tooltips) phases.js ← Maps raw robot stages to friendly names

What is a "hook"?

In React, a hook is a reusable piece of logic that a component can "hook into." For example, useRagCaption.js knows how to call the AI server and manage the loading/error states. Any component that needs an AI caption can use this hook instead of writing the same fetch-and-wait logic from scratch.

5. The Live Screen

This is what the employee looks at during their shift. It shows:

ComponentWhat it shows
AttentionPanelThe current order: what item, which stage, a progress bar, and buttons to intervene if needed
WorkflowTimelineA vertical timeline showing all 7 phases of the robot's work, with green checkmarks for completed steps
RobotStatusCardHardware status: is the gripper open/closed? Camera working? Any errors?

The 7 phases of a robot order

Every order follows the same pipeline, defined in src/lib/phases.js:

#PhaseWhat happens
1Going to the shelfRobot plans a path and drives to the shelf location
2Finding the itemCamera takes a photo, AI (SAM3) detects items, picks the best match
3Analyzing the graspAnother AI (Molmo) figures out exactly where and how to grab it
4Picking it upGripper opens, descends, closes around the item, lifts
5Bringing it overRobot arm moves the item to the handover desk
6Handing overGripper opens to release the item for the employee
7ReturningRobot goes back to the shelf, ready for the next order

Employee intervention

Sometimes the robot's camera can't find the requested item (maybe it's been moved or the shelf is empty). When this happens:

  1. The dashboard turns orange and shows "Intervention needed"
  2. The employee can tap a button to tell the robot to try again
  3. The app sends a message back through the WebSocket to the server
  4. The server resumes the robot's pipeline

If nobody responds within 2 minutes, the order is marked as failed and the robot moves on.

A bar chart showing daily activity. Each day has a stacked bar with three colors: green (delivered), amber (delivered with warnings), and red (failed). A filterable list of all orders, grouped by date. Each order shows:

  • The item name and order number
  • How long it took and when it finished
  • A status pill ("Delivered", "Delivered with warnings", "Couldn't deliver")

Tapping an order expands it to show the step-by-step phases with timing and technical details. There's also a "Why so long? Ask ROBI" button that opens the chat pre-filled with a question about that specific order.

Chat Panel

src/features/history/components/ChatPanel.jsx

A slide-in panel where the employee can ask ROBI's AI assistant questions in natural language. The AI streams its response word-by-word (like ChatGPT) and can reference specific orders and technical terms.

7. The AI Brain (RAG Server)

src/rag/server.py

This is a Python program that runs alongside the web app. It connects to Ollama, which is a tool that runs AI language models locally on your computer (no internet required, no data sent to the cloud).

What is Ollama?

Ollama is like having a small ChatGPT running on your own machine. We use two AI models through it:

ModelPurposeAnalogy
qwen2.5:3bLanguage model — writes summaries, answers questionsThe writer who reads facts and produces a report
nomic-embed-textEmbedding model — converts text to numbers for searchingThe librarian who knows which books are about similar topics

The RAG server's jobs

  1. Caption generation: The History screen asks "Write me a summary for this week's chart." The server gathers the real numbers, writes a prompt with those facts, sends it to the AI model, and returns the AI's text.
  2. Chat: The employee asks a question. The server searches for relevant orders, adds them as context, and streams the AI's answer back word-by-word.
  3. Caching: AI responses are saved to disk so the same question doesn't need to be re-generated. Old data that can't change anymore (e.g., last week's summary) is cached forever.

8. How RAG Works in Our Case

RAG stands for Retrieval-Augmented Generation. Let's break that down:

The problem: The AI language model (qwen2.5:3b) doesn't know anything about ROBI's orders. It's a general-purpose writer. If you just ask it "How did ROBI do this week?", it would make something up.

The solution: Before asking the AI to write, we retrieve the actual data, put it in the prompt as facts, and then ask the AI to write about those facts. The AI never invents numbers — it only phrases them.

Step-by-step: How a caption gets generated

When you open the History page and it needs a weekly summary:

1. Frontend: "I need a weekly caption" | v 2. RAG Server checks cache: "Have I already written this?" - If yes: return the cached version instantly - If no: continue... | v 3. RAG Server reads data/orders.json Computes stats IN PYTHON (not AI!): - 187 delivered, 5 with warnings, 20 failed - Average time: 115 seconds - Busiest day: Monday with 179 orders - Top failure: gripper_failed (12 times) | v 4. RAG Server builds a prompt: "Write a 2-paragraph weekly summary. FACTS: 1. Orders this week: 212 (187 delivered, 5 warnings, 20 failed) 2. Average fetch time: 115 seconds 3. Busiest day: Monday with 179 orders ..." | v 5. Sends prompt to Ollama (local AI model) | v 6. AI writes: "This week, ROBI handled 212 orders with a strong 88% delivery rate. The [[gripper]] performed well on most items..." | v 7. Post-processor wraps any missed technical terms in [[brackets]] | v 8. Response cached to disk, returned to frontend | v 9. SmartCaption component renders [[gripper]] as a teal-underlined tooltip, [cite:42] as a clickable chip

Why "deterministic stats"?

A critical rule in our system: the AI never does math. All numbers (counts, averages, percentages) are calculated by Python code. The AI model only receives pre-computed facts and writes prose about them. This prevents the AI from inventing wrong numbers like "ROBI delivered 300 orders" when the real number is 187.

The FAISS vector index (for chat)

When the employee asks a free-form question in the chat (like "Which orders had gripper problems?"), we need to find relevant orders to include as context. This is where FAISS comes in.

Imagine you have 200 order cards. You want to find the ones most relevant to a question. FAISS is like a magical card sorter — it converts each order into a list of numbers (a "vector") that represents its meaning, then quickly finds which orders are most similar to the question.

  1. On startup, every order is converted to a text description ("Order #42: ballpoint pen, delivered, 95s total, phases: finding, grasping...")
  2. Each description is sent through the nomic-embed-text model, which converts it into 768 numbers (a "vector")
  3. All vectors are stored in a FAISS index (a fast search structure)
  4. When a chat question arrives, the question is also converted to a vector
  5. FAISS finds the 6 most similar orders and includes them in the AI prompt as context

9. Smart Captions - Terms, Citations, and Suggestions

src/components/ui/SmartCaption.jsx

AI-generated text isn't just plain text — it contains special markers that the frontend renders as interactive elements:

MarkerExampleWhat it renders as
[[slug]][[gripper]]A teal-underlined word that shows a tooltip on hover explaining what a "gripper" is
[cite:N][cite:42]A small clickable chip "#42" that scrolls to that order in the list
**text****Suggestion: check the gripper**Bold teal text that visually highlights the actionable recommendation

The terms dictionary

src/lib/terms.js

Contains 14 technical terms with plain-English definitions. When the AI mentions "gripper" or "SAM3" or "trajectory," the tooltip explains what it means to a non-technical employee. The AI is instructed to use [[slug]] markers, and a post-processor ensures they're present even if the AI forgets.

The wrap_terms() post-processor

After every AI response, a Python function scans the text and wraps the first mention of each known technical term in [[brackets]] if the AI didn't already do it. This is a safety net so tooltips always work, regardless of AI behavior.

10. Order Statuses - Green, Amber, Red

Every order ROBI processes gets classified into one of three statuses:

StatusColorLabelWhat it means
successEmeraldDeliveredROBI picked up the item and handed it over with no problems
warningAmberDelivered with warningsROBI delivered the item, but something went wrong along the way (e.g., camera couldn't find the item at first, had to retry)
failedRoseCouldn't deliverROBI could not complete the order (gripper failure, timeout, emergency stop, etc.)

How the classification works

Inside the WebSocket server, every robot cycle tracks a list of "failures" at two severity levels:

  • Red-level: Critical problems — gripper failure, emergency stop, robot error. These make the order failed.
  • Orange-level: Recoverable problems — 0 detections on first try (but the robot recovered and delivered). These make the order warning.
  • No failures: Everything went smoothly. The order is success.

This three-way classification appears everywhere: tally tiles in the chart, bar chart colors, filter chips in the orders list, status icons, and status pills on each order row.

data/orders.json | | (read by both servers) v +-----+-----------+ | | v v ws-test-server rag/server.py (port 8765) (port 5175) | | | HTTP GET | HTTP POST | /api/orders/daily | /api/rag/caption | /api/orders/list | /api/rag/chat (SSE) | | v v ActivityChart useRagCaption hook / useRagChat hook OrdersList | (tally tiles, v bar chart, AiCaption component order rows) ChatPanel component WeeklySummaryCard
Key insight: The left side (data) and right side (AI) are completely independent. If the AI server crashes, the chart and orders still work perfectly. This was a deliberate design choice so the core functionality never depends on AI availability.

13. What Happens When...

...you open the History page?

  1. HistoryScreen mounts with "Week" selected (default)
  2. ActivityChart sends GET http://localhost:8765/api/orders/daily?from=2026-05-06&to=2026-05-12
  3. OrdersList sends GET http://localhost:8765/api/orders/list?from=2026-05-06&to=2026-05-12&status=all&item=all
  4. Both components independently call useRagCaption, which sends POST http://localhost:5175/api/rag/caption
  5. WeeklySummaryCard also calls useRagCaption('weekly')
  6. Tally tiles and chart render immediately from step 2's response
  7. AI captions show a pulsing skeleton while loading, then render when the AI responds

...you click "Month" instead of "Week"?

  1. HistoryScreen updates dateFrom to 30 days ago
  2. Both ActivityChart and OrdersList re-fetch with the new date range
  3. Both AI captions re-fetch with the new scope (and may use cache if available)
  4. The chart trims leading empty days so it doesn't show 28 blank bars
  5. Bar widths shrink and x-axis labels thin out for the wider range

...you tap the "Warnings" filter chip?

  1. OrdersList re-fetches with status=warning
  2. The AI caption re-fetches with the warning-specific scope
  3. The RAG server filters orders to only warning orders before computing stats
  4. A warning-specific prompt is used: "Explain what 'delivered with warnings' means, identify patterns, give a concrete suggestion"
  5. The response includes **Suggestion:** text rendered in teal bold

...you click "Why so long? Ask ROBI" on an order?

  1. HistoryScreen sets chatPrefill to "Why did order #42 take 180s?"
  2. ChatPanel opens and detects the prefill
  3. It automatically sends the prefilled question via useRagChat
  4. The RAG server searches FAISS for orders similar to the question
  5. It builds context with the matched orders + weekly stats
  6. The AI streams its answer word-by-word via Server-Sent Events (SSE)
  7. The chat updates in real time as each word arrives

...the AI server (Ollama) is not running?

  1. The frontend still loads — charts, numbers, orders all work fine (data comes from WS server)
  2. AI caption requests timeout after 15 seconds
  3. The caption shows "ROBI's report is unavailable right now — local AI is offline"
  4. Chat panel shows an error message if you try to send a message
  5. Nothing crashes. The page is fully usable without AI.
